# Code maturity assessment

Date: 2026-07-26

Scope: Launcher’s Solidity workspace and its deployment, specification, test and security evidence. Upstream Uniswap/OpenZeppelin code is treated as an external dependency, not as maturity credit for Launcher.

## Executive summary

Overall maturity: **2.3 / 4.0, Moderate**

The strongest parts are the immutable authority model, narrow composition around pinned upstream contracts and unusually substantial local/fork testing for a protocol spike. The largest gaps are operational rather than cosmetic: there is no independent audit, no live monitoring or tested incident response, no signed Sepolia evidence and no production frontend simulation path.

This score is not a safety rating and does not approve deployment.

## Detailed assessment

### Arithmetic — Moderate

Evidence:

- Solidity 0.8.26 checked arithmetic and a Cancun target are fixed in `foundry.toml:7-10`.
- Native and token budgets are capped at `uint128`, and invalid price bounds revert in `src/DirectLiquidityLauncherV1.sol:331-349`.
- Actual liquidity is derived from the upstream planner remainder with checked subtraction in `src/DirectLiquidityLauncherV1.sol:215-226`.
- Budget accounting is fuzzed in `test/DirectLiquidityLauncherV1.t.sol:319-340`.
- The hook’s 0.10% rate is a constant and uses the upstream fee base in `src/PlatformFeeHookV1.sol:25-32` and `src/PlatformFeeHookV1.sol:146-155`.

Gap: direct-launch branch coverage is 42.11%, pathological upstream math boundaries are not independently proven and no symbolic arithmetic proof exists.

Next level: add boundary-specific tick/price tests, differential tests against an independent liquidity calculator and formal properties for conservation and rounding.

### Auditing — Moderate

Evidence:

- Direct launches emit both identity and exact liquidity-budget records in `src/DirectLiquidityLauncherV1.sol:79-98` and `src/DirectLiquidityLauncherV1.sol:229-273`.
- Platform collections emit caller, fixed recipient, currency and amount in `src/PlatformFeeHookV1.sol:58-60` and `src/PlatformFeeHookV1.sol:177-184`.
- Factory deployments emit complete immutable configuration records.
- `security/MONITORING-AND-INCIDENT-RESPONSE.md` defines event reconciliation, severity, response steps and the missing ownership assignments.

Gap: no deployed indexer consumes these events, no alert delivery exists and no incident-response exercise or accountable response role is assigned. A specification alone does not prove operational coverage.

Next level: deploy a reorg-safe indexer, alert on unknown code/configuration, reconcile fee and LP state, publish an incident runbook and test it on Sepolia.

### Authentication and access control — Satisfactory

Evidence:

- The hook initializer, fee recipient, currencies and PoolId are immutable in `src/PlatformFeeHookV1.sol:34-50`.
- Only the immutable initializer can initialize the exact pool in `src/PlatformFeeHookV1.sol:139-143`.
- Only PoolManager can invoke the fee redemption callback in `src/PlatformFeeHookV1.sol:157-169`.
- The direct launcher exposes one permissionless state-changing method and has no privileged method in `src/DirectLiquidityLauncherV1.sol:150-177`.
- The LP forwarder policy fixes a zero operator and maximum timelock in `src/LockedPositionFeeForwarderFactoryV1.sol:13-23`.

Gap: the immutable treasury is currently an EOA, so key compromise can redirect neither pools nor user principal but can compromise collected platform revenue.

Next level: select and test a production Safe policy before deploying new immutable hooks.

### Complexity management — Satisfactory

Evidence:

- Slither’s function summary measured a maximum cyclomatic complexity of 7.
- The direct launcher separates validation, deterministic deployment, token creation, liquidity planning and record creation in `src/DirectLiquidityLauncherV1.sol:157-176` and `src/DirectLiquidityLauncherV1.sol:179-350`.
- Product variants are composed across five explicit axes rather than duplicated as unrelated contracts in `spec/launch-variants.v1.json:9-15`.

Gap: the composition relies on several sophisticated upstream systems, so operational comprehension still exceeds the apparent size of Launcher’s own code.

Next level: maintain per-variant sequence diagrams and threat models as each new hook family is added.

### Decentralization — Satisfactory

Evidence:

- There is no owner, proxy, pause, upgrade or mutable fee.
- Anyone can deploy through the factories and anyone can trigger fee forwarding.
- The LP position cannot be transferred or reduced under the selected policy, while LP fees go only to the immutable creator; this boundary is specified in `spec/direct-standard-v1.json:28-48`.
- The platform treasury receives only the separately disclosed fixed hook fee.

Gap: immutable deployment choices cannot be repaired in place. A bad treasury or dependency selection requires a new version, and a creator cannot recover intentionally locked initial liquidity.

Next level: publish a version registry and explicit deprecation policy without adding upgrade authority.

### Documentation — Moderate

Evidence:

- Auction and direct standards are machine-readable and explicitly set `productionApproved` to false in `spec/direct-standard-v1.json:1-56`.
- Variant status semantics distinguish tested, planned and research work in `spec/launch-variants.v1.json:1-7`.
- Security properties, deployment instructions, architecture, function and authorization diagrams are checked in.
- Dependency addresses, source refs and runtime hashes are pinned and verified.

Gap: there is no complete glossary, operator handbook, indexer specification, end-user risk disclosure set or public deployment evidence.

Next level: add those documents and generate human-facing launch disclosures from the same validated specifications.

### Transaction ordering risks — Moderate

Evidence:

- The direct launcher safely reuses only factory-recorded matching CREATE2 artifacts in `src/DirectLiquidityLauncherV1.sol:276-314`.
- The predeployment regression is tested in `test/DirectLiquidityLauncherV1.t.sol:299-317`.
- The bound hook prevents another caller from initializing the pool.

Gap: initial price and budgets are public in the mempool. Searchers can back-run and arbitrage a poor creator-selected price. The product has no private-transaction integration or objective price guard.

Next level: add explicit price-impact simulation, optional private delivery and ordering-focused Sepolia tests. Do not describe these controls as sandwich prevention.

### Low-level manipulation — Moderate

Evidence:

- Launcher’s production source contains no inline assembly, delegatecall, selfdestruct, raw call or custom signature recovery.
- CREATE2 uses OpenZeppelin and the transient reentrancy lock uses OpenZeppelin.
- Hook fee arithmetic uses OpenZeppelin’s Uniswap hook base and Uniswap math.
- Dependency commits and eight runtime hashes are checked before Sepolia deployment in `script/DeploySepoliaInfrastructureV1.s.sol:31-43` and `script/DeploySepoliaInfrastructureV1.s.sol:78-97`.

Gap: the trusted upstream graph contains assembly and transient-storage code. Launcher has not run independent differential tests for every such primitive.

Next level: add differential reference tests for liquidity calculation and preserve upstream audit/version evidence per release.

### Testing and verification — Moderate

Evidence:

- 41 tests pass across unit, integration, fork, fuzz and stateful invariant suites.
- Measured coverage is 93.75% lines and 91.80% statements; the direct launcher reaches 94.44% lines and 100% functions.
- Local fuzz and invariant profiles are defined in `foundry.toml:20-31`.
- The CI workflow pins every external action by commit and runs frontend verification, contract verification, the live official-deployment check and Slither in `.github/workflows/verify.yml:16-75`.
- GitHub Actions run [30182711094](https://github.com/hazarxyz/launcher-v4/actions/runs/30182711094) passed both jobs for commit `361fc8a3ac54a8a0adca25f555e1aae6b67cece3`.
- The Sepolia deployment test checks the complete three-contract infrastructure composition.

Gap: there is no mutation testing, symbolic execution, independent audit or signed testnet E2E.

Next level: require the remote checks, add mutation/failure injection, complete the Sepolia lifecycle and commission an independent review.

## Improvement roadmap

### Critical before any public testnet claim

1. Fund and sign the exact Sepolia rehearsal, preserve receipts and verify source code. Estimated effort: 0.5–1 day after signer access.
2. Build frontend calldata generation plus chain, address, codehash, balance-change and simulation gates. Estimated effort: 3–5 days.
3. Run direct and auction E2E launches through swaps and both fee paths. Estimated effort: 1–2 days.

### High before mainnet

1. Independent audit or public contest, remediation and regression suite. Estimated effort: 3–6 weeks including reviewer lead time.
2. Reorg-safe indexing, alerting, reconciliation and a tested incident process. Estimated effort: 1–2 weeks.
3. Production Safe treasury and deployment-signer policy. Estimated effort: 2–4 days plus owner decisions.
4. Legal product boundary for securities, RWA representations and unsupported claims. Timeline depends on counsel.

### Medium for the broader variant catalog

1. Differential liquidity/accounting tests and symbolic properties. Estimated effort: 1–2 weeks.
2. Per-module compatibility matrices and threat models for fee split, timed opening and dynamic fees. Estimated effort: 2–4 days per module before implementation.
3. Isolated unverified-hook analysis, source/proxy disclosure and bytecode simulation lane. Estimated effort: 2–4 weeks.
