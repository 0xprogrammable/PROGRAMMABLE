# Protocol security review

Date: 2026-07-26

Scope: `PlatformFeeHookV1.sol`, `PlatformFeeHookFactoryV1.sol`, `LockedPositionFeeForwarderFactoryV1.sol`, `DirectLiquidityLauncherV1.sol`, the standard-auction transaction builder and server preflight, plus their pinned Uniswap/OpenZeppelin dependencies.

Verdict: suitable for continued fork and Sepolia rehearsal work. Not audited, deployed or approved for mainnet.

## Secure development workflow

### 1. Static analysis

Slither analyzed 88 contracts with 101 detectors and returned zero findings. The machine-readable result is stored in `slither-results.json`.

The first direct-launch pass identified an unchecked `PoolManager.initialize` result and unused `PositionPlanner` remainder values. The implementation now checks the returned initial tick and records actual liquidity from the planner’s remainder. Slither’s reentrancy warnings on both atomic entry points were false positives caused by its lack of support for OpenZeppelin’s transient reentrancy guard and are suppressed only at the exact guarded sites.

A manual transaction-ordering pass found a separate issue that static analysis did not report: an observer could predeploy the exact CREATE2 hook or position forwarder through the permissionless factories and make the original launch transaction revert. The direct launcher now reuses only a factory-recorded deployment whose immutable configuration matches. The regression case predeploys both artifacts before launching.

### 2. Special features

- Upgradeability: no proxy, initializer, upgrade, delegatecall, owner, pause or arbitrary-call path exists in Launcher’s production contracts. Upgradeability checks are therefore not applicable to this version.
- ERC-165: `slither-check-erc` confirms `PlatformFeeHookV1.supportsInterface(bytes4)` has the required signature and return type.
- ERC-20 integration: the new-token direct path creates only the pinned Uniswap UERC20 implementation. The existing-token path reconstructs the token’s CREATE2 address through the configured UERC20Factory and requires its recorded creator. The ERC checker found every required ERC-20 function and event. Its event-emission warnings are caused by Solady’s assembly implementation, and its approval-race warning describes the standard ERC-20 allowance behavior rather than a Launcher-specific deviation.
- External tokens: arbitrary existing tokens, transfer-tax tokens, rebasing tokens and proxies remain outside the protocol-tested boundary.

### 4. Security properties and property testing

`SECURITY-PROPERTIES.md` defines the hook, fee, custody, provenance, auction, direct-accounting and atomicity properties. Foundry supplies the executable fuzz and invariant infrastructure, while Vitest decodes the exact official LiquidityLauncher multicall and checks the canonical CCA fixture:

- 1,000 fee-reference fuzz cases per local run
- 64 direct native/token budget pairs locally and 256 under the CI profile
- 64 existing-token native/token budget pairs locally and 256 under the CI profile
- 256 invariant runs at depth 64, or 16,384 state-changing calls per property
- zero invariant handler reverts

Echidna and Manticore are not installed in this environment. The Foundry properties run now; symbolic execution and an independent property suite remain pre-mainnet work rather than being represented as completed.

### 5. Manual review

#### Access control and custody

There is no Launcher administrator. Pool callbacks are restricted by OpenZeppelin `BaseHook.onlyPoolManager`. Each hook accepts one immutable initializer and one complete `PoolId`. The direct launcher can initialize only the pool already bound into the hook it deploys.

The initial LP NFT is minted directly to the pinned official `PositionFeesForwarder`. The operator is the zero address, the approval block is `type(uint256).max` and the creator is the immutable LP-fee recipient. For an existing token, the caller must first match the creator recorded by its UERC20 deployment. Neither the creator nor the platform can transfer the initial position or remove its liquidity through this configuration. Anyone may trigger fee collection but cannot change either payout address.

#### Reentrancy and atomicity

Both direct entry points use OpenZeppelin’s Cancun-compatible `ReentrancyGuardTransient` around the complete external-call sequence. Hook deployment, forwarder deployment, optional token creation or exact token transfer, pool initialization, position minting and launch-record creation share one transaction. A failure rolls all of them back.

PositionManager returns unused native and token budgets directly to the creator. The launcher then returns the rest of the fixed token supply and retains no launched tokens. Native ETH forcibly sent with `selfdestruct` would remain stranded because the contract intentionally has no rescue or administrator; it cannot be attributed to or taken from a later launch.

The auction path uses two deterministic setup transactions and then one official LiquidityLauncher multicall. The final call creates the fixed-supply UERC20 and distributes its complete supply to LBPStrategy atomically. A failure cannot leave a reusable token address because the creator-bound token creation and distribution roll back together.

#### Arithmetic and price

Solidity 0.8.26 provides checked arithmetic. Native and token liquidity budgets are capped at `uint128`, matching the upstream liquidity planner’s relevant bounds. Actual use is calculated by checked subtraction from the planner’s returned remainder and fuzzed against both caller budgets.

The creator supplies `initialSqrtPriceX96`. The launcher validates the v4 TickMath range and checks that PoolManager returns the expected tick. It has no oracle and makes no claim that the chosen opening price is economically correct.

Fee math is inherited from OpenZeppelin `BaseHookFee` and Uniswap `FullMath`, rounding down. The platform fee is fixed at 1,000 / 1,000,000, or 0.10%.

The auction valuation path uses integer arithmetic only. It converts the requested full-supply valuation to raw-currency-per-raw-token Q96, snaps the floor down through the official SDK and rejects values outside the CCA supply, floor, tick and liquidity bounds. At the standard 50% sale allocation, the graduation threshold is the snapped cost of the auction half rather than an independently entered funding target.

#### Transaction ordering and MEV

The factory-predeployment griefing path is mitigated by verified reuse. Token-address theft is not possible through UERC20Factory because the CREATE2 identity includes the direct launcher as the factory caller and a creator-bound graffiti value.

The launch transaction exposes the selected initial price and liquidity budgets in the mempool. No transaction can initialize the bound pool before the authorized launcher, but searchers can back-run the newly opened pool and arbitrage a poor opening price. Private transaction delivery may reduce exposure; it cannot replace price review. The hook adds no sandwich protection.

Auction setup addresses are deterministic and may be deployed first by another caller, but only through the bytecode-verified factories and with the same immutable configuration. The server reuses those deployments after provenance checks. It refreshes stale auction timing before signing and leaves at least 20 preparation blocks. CCA bids remain public and ordering-dependent by design; Launcher does not claim to remove auction MEV.

#### Dependency and token assumptions

The constructor checks that every dependency has code, PositionManager names the selected PoolManager and the forwarder factory names the selected PositionManager. The Sepolia script additionally checks eight official runtime-code hashes. Deployment on another network with merely code-bearing but malicious dependencies would not inherit the protocol-tested status.

For the Mainnet auction path, the preflight additionally reads the official LBPStrategy’s PoolManager, PositionManager and initializer factory. It requires the pinned CCA factory’s protocol fee controller to be the zero address before stating that all auction proceeds fund the pool. The same policy is asserted at the pinned Ethereum fork block.

The created token is the fixed-supply, 18-decimal UERC20 from the pinned official factory. It has no transfer tax, blacklist, rebase, proxy or second mint. The existing-token method accepts the same fixed UERC20 implementation with factory-defined decimals only when the configured factory reproduces its address and the recorded creator calls. Indexers must distinguish new-token, existing-token and complete official auction launch records.

Creator contracts must be able to receive native ETH when PositionManager returns launch dust and when LP fees are forwarded. A rejecting receive function can make those operations revert. Frontend simulation must detect this before signing.

#### Privacy and cryptography

The contracts store no secrets and use no signatures, randomness, oracle or custom cryptographic primitive. CREATE2 is used only for deterministic addresses and hook callback bits. Launch parameters are public before inclusion.

## Remaining blockers

1. Fund the test wallet with approximately 0.04 Sepolia ETH and perform a signed, receipt-checked deployment rehearsal.
2. Execute complete Sepolia launches for the auction, new-token direct and existing-UERC20 direct variants, then verify swaps, platform-fee collection, LP-fee collection and failure recovery.
3. Verify every deployed source and bind runtime bytecode to the exact Git commit.
4. Rehearse the frontend-generated calldata and every fail-closed chain, address, codehash, balance and simulation gate against the signed Sepolia deployment.
5. Establish production treasury custody, signer policy, event monitoring and an incident-response process.
6. Commission an independent audit or public review and resolve every accepted finding.
7. Recheck the official Uniswap deployment registry, CCA fee-controller policy and runtime bytecode immediately before release.
8. Obtain legal review and block unsupported securities, RWA or custody claims.

No mainnet deployment should occur until these gates are closed.
