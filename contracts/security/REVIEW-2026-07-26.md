# Protocol security review

Date: 2026-07-26

Scope: `PlatformFeeHookV1.sol`, `PlatformFeeHookFactoryV1.sol`, `LockedPositionFeeForwarderFactoryV1.sol`, `DirectLiquidityLauncherV1.sol` and their pinned Uniswap/OpenZeppelin dependencies.

Verdict: suitable for continued fork and Sepolia rehearsal work. Not audited, deployed or approved for mainnet.

## Secure development workflow

### 1. Static analysis

Slither analyzed 88 contracts with 101 detectors and returned zero findings. The machine-readable result is stored in `slither-results.json`.

The first direct-launch pass identified an unchecked `PoolManager.initialize` result and unused `PositionPlanner` remainder values. The implementation now checks the returned initial tick and records actual liquidity from the planner’s remainder. Slither’s remaining reentrancy warning was a false positive caused by its lack of support for OpenZeppelin’s transient reentrancy guard and is suppressed on the exact protected line.

A manual transaction-ordering pass found a separate issue that static analysis did not report: an observer could predeploy the exact CREATE2 hook or position forwarder through the permissionless factories and make the original launch transaction revert. The direct launcher now reuses only a factory-recorded deployment whose immutable configuration matches. The regression case predeploys both artifacts before launching.

### 2. Special features

- Upgradeability: no proxy, initializer, upgrade, delegatecall, owner, pause or arbitrary-call path exists in Launcher’s production contracts. Upgradeability checks are therefore not applicable to this version.
- ERC-165: `slither-check-erc` confirms `PlatformFeeHookV1.supportsInterface(bytes4)` has the required signature and return type.
- ERC-20 integration: the direct path creates only the pinned Uniswap UERC20 implementation. The ERC checker found every required ERC-20 function and event. Its event-emission warnings are caused by Solady’s assembly implementation, and its approval-race warning describes the standard ERC-20 allowance behavior rather than a Launcher-specific deviation.
- External tokens: arbitrary existing tokens, transfer-tax tokens, rebasing tokens and proxies remain outside the protocol-tested boundary.

### 3. Visual inspection

Slither’s inheritance graph is stored in `diagrams/inheritance-graph.dot`. The generated function and authorization views are summarized in `diagrams/function-surface.md` and `diagrams/state-authorization.md`; the end-to-end composition is in `diagrams/architecture.md`.

The function view found three direct-launcher entry points. Two are read-only predictions and `launch` is the only state-changing entry point. The highest cyclomatic complexity is 7. The authorization view found one mutable direct-launcher mapping, `launchHashOf`, written only after a successful atomic launch. All authorities and recipients are immutable.

### 4. Security properties and property testing

`SECURITY-PROPERTIES.md` defines the hook, fee, custody, provenance, direct-accounting and atomicity properties. Foundry supplies the executable fuzz and invariant infrastructure:

- 1,000 fee-reference fuzz cases per local run
- 64 direct native/token budget pairs locally and 256 under the CI profile
- 256 invariant runs at depth 64, or 16,384 state-changing calls per property
- zero invariant handler reverts

Echidna and Manticore are not installed in this environment. The Foundry properties run now; symbolic execution and an independent property suite remain pre-mainnet work rather than being represented as completed.

### 5. Manual review

#### Access control and custody

There is no Launcher administrator. Pool callbacks are restricted by OpenZeppelin `BaseHook.onlyPoolManager`. Each hook accepts one immutable initializer and one complete `PoolId`. The direct launcher can initialize only the pool already bound into the hook it deploys.

The initial LP NFT is minted directly to the pinned official `PositionFeesForwarder`. The operator is the zero address, the approval block is `type(uint256).max` and the creator is the immutable LP-fee recipient. Neither the creator nor the platform can transfer the initial position or remove its liquidity through this configuration. Anyone may trigger fee collection but cannot change either payout address.

#### Reentrancy and atomicity

`launch` uses OpenZeppelin’s Cancun-compatible `ReentrancyGuardTransient` around the complete external-call sequence. Hook deployment, forwarder deployment, token creation, pool initialization, position minting and launch-record creation share one transaction. A failure rolls all of them back.

PositionManager returns unused native and token budgets directly to the creator. The launcher then returns the rest of the fixed token supply and retains no launched tokens. Native ETH forcibly sent with `selfdestruct` would remain stranded because the contract intentionally has no rescue or administrator; it cannot be attributed to or taken from a later launch.

#### Arithmetic and price

Solidity 0.8.26 provides checked arithmetic. Native and token liquidity budgets are capped at `uint128`, matching the upstream liquidity planner’s relevant bounds. Actual use is calculated by checked subtraction from the planner’s returned remainder and fuzzed against both caller budgets.

The creator supplies `initialSqrtPriceX96`. The launcher validates the v4 TickMath range and checks that PoolManager returns the expected tick. It has no oracle and makes no claim that the chosen opening price is economically correct.

Fee math is inherited from OpenZeppelin `BaseHookFee` and Uniswap `FullMath`, rounding down. The platform fee is fixed at 1,000 / 1,000,000, or 0.10%.

#### Transaction ordering and MEV

The factory-predeployment griefing path is mitigated by verified reuse. Token-address theft is not possible through UERC20Factory because the CREATE2 identity includes the direct launcher as the factory caller and a creator-bound graffiti value.

The launch transaction exposes the selected initial price and liquidity budgets in the mempool. No transaction can initialize the bound pool before the authorized launcher, but searchers can back-run the newly opened pool and arbitrage a poor opening price. Private transaction delivery may reduce exposure; it cannot replace price review. The hook adds no sandwich protection.

#### Dependency and token assumptions

The constructor checks that every dependency has code, PositionManager names the selected PoolManager and the forwarder factory names the selected PositionManager. The Sepolia script additionally checks eight official runtime-code hashes. Deployment on another network with merely code-bearing but malicious dependencies would not inherit the protocol-tested status.

The created token is the fixed-supply, 18-decimal UERC20 from the pinned official factory. It has no transfer tax, blacklist, rebase, proxy or second mint. A successful factory deployment alone is not a verified Launcher token; indexers must require the direct launch record or the complete official auction path.

Creator contracts must be able to receive native ETH when PositionManager returns launch dust and when LP fees are forwarded. A rejecting receive function can make those operations revert. Frontend simulation must detect this before signing.

#### Privacy and cryptography

The contracts store no secrets and use no signatures, randomness, oracle or custom cryptographic primitive. CREATE2 is used only for deterministic addresses and hook callback bits. Launch parameters are public before inclusion.

## Remaining blockers

1. Fund the test wallet with approximately 0.03 Sepolia ETH and perform a signed, receipt-checked deployment rehearsal.
2. Execute complete Sepolia launches for both auction and direct variants, then verify swaps, platform-fee collection, LP-fee collection and failure recovery.
3. Verify every deployed source and bind runtime bytecode to the exact Git commit.
4. Build frontend calldata from the machine-readable specifications and require chain-ID, address, codehash, balance-change and simulation checks before signing.
5. Establish production treasury custody, signer policy, event monitoring and an incident-response process.
6. Commission an independent audit or public review and resolve every accepted finding.
7. Recheck the official Uniswap deployment registry and runtime bytecode immediately before release.
8. Obtain legal review and block unsupported securities, RWA or custody claims.

No mainnet deployment should occur until these gates are closed.
