# Protocol spike security review

Date: 2026-07-26
Scope: `PlatformFeeHookV1.sol`, `PlatformFeeHookFactoryV1.sol`
Verdict: suitable for continued fork and testnet work; not approved for mainnet

## Automated results

- Foundry build: pass with Solidity 0.8.26, Cancun EVM and optimizer enabled
- Tests: 24 pass, 0 fail, including unit, integration, fork, fuzz and invariant suites
- Production-contract coverage: hook 100% lines and 98% statements; factory 94.44% lines and 95.45% statements
- Fee fuzzing: 1,000 cases in the default profile
- Stateful invariants: 256 runs, depth 64, 16,384 calls per property, zero reverts
- Ethereum fork snapshot: eight official deployment bytecode hashes match block 25,612,664
- Slither: 0 findings across 101 detectors after two code corrections and one documented false-positive suppression
- ERC-165 conformance check: pass
- Hook runtime size: 7,986 bytes
- Factory runtime size: 11,212 bytes
- Hook storage layout: empty; all configuration is constant or immutable
- Factory storage layout: one provenance mapping

The Slither pass initially reported an ignored `PoolManager.unlock` return value and event placement after external interactions. The implementation now validates the empty callback result and emits before interactions, with transaction rollback preserving event correctness on failure. Slither’s `too-many-digits` detector misclassifies the CREATE2 init-code hash expression; that single line is suppressed inline.

The integration suite exercises the official CCA factory and auction source through a recording wrapper: a native-ETH bid is submitted, the auction is finalized and graduated, and LBPStrategy migrates it into the hook-bound pool. A separate test double remains for narrow launch-path assertions.

## Manual review

### Access control

There is no administrator. Pool callbacks are restricted by OpenZeppelin `BaseHook.onlyPoolManager`. Initialization additionally checks the immutable authorized strategy and the complete `PoolId`. Permissionless fee collection cannot select currencies or a recipient.

### Upgradeability and storage

Neither contract is upgradeable. The hook has no mutable storage. The factory’s mapping is append-only provenance for successful factory deployments. A new implementation requires a new bytecode address and should receive a new compatibility ID.

### Reentrancy and external calls

Collection enters PoolManager’s unlock flow, burns the hook’s ERC-6909 claims and takes underlying assets to the immutable recipient. The hook changes no mutable state. A recipient contract can make its own native payout fail through a reverting fallback, but cannot redirect or steal claims; a failed transaction leaves the claims intact.

The immutable fee recipient should nevertheless be a tested Safe-style treasury whose receive path does not intentionally revert. This address is still undecided.

### Arithmetic

Fee math is inherited from OpenZeppelin `BaseHookFee` and uses Uniswap `FullMath.mulDiv`, rounding down. The rate is 1,000 / 1,000,000. The hook never performs custom price, tick or liquidity arithmetic.

### MEV and market behavior

The hook adds a deterministic fee after core swap accounting. It does not read an oracle, change LP fees, create a custom curve or branch on the trader. It adds no new price-discovery or sandwich defense. Auction design and migration timing remain upstream LBP and CCA concerns.

### Token behavior

The verified V1 path is restricted to fixed-supply UERC20 tokens. Transfer-tax, rebasing and arbitrary external tokens are outside the badge boundary. Integration tests cover both ERC-20 and native fee redemption.

### Denial of service

Invalid pool parameters, wrong initializer, wrong hook address bits and failed recipient transfers revert safely. The immutable recipient can self-deny fee redemption by rejecting native ETH. There is no rescue or alternate-recipient escape hatch by design; changing that would reintroduce administrative trust.

### Privacy and cryptography

The contracts store no private data and implement no custom cryptography. CREATE2 is used only for deterministic hook-address permissions.

## Remaining blockers

1. The exact production CCA factory sender/salt path, protocol-fee controller and final auction schedule still require a Sepolia rehearsal.
2. The intended permanent LP-position recipient and fee-forwarding policy are not integrated.
3. The treasury address, deployment account model and incident process are undecided.
4. No independent audit or public contest has reviewed Launcher’s contracts.
5. Sepolia deployment, source verification, reproducibility and UI transaction simulation are not complete.
6. Official deployment addresses and runtime bytecode must be checked again immediately before release.

No mainnet deployment should occur until all six blockers are closed.
