# Scenario matrix

Use this matrix after the idea brief. Apply every row whose trigger is present. More than one row usually applies.

`Automated gate` means a deterministic check can pass or fail. `Review gate` identifies a decision that requires human
judgment.

`v4-protocol-mechanics.md` is the canonical source-level account of callback response shapes, return-delta signs,
settlement, claims, and core fee composition. The v4 rows below select questions and evidence; they do not redefine
those mechanics.

## Packaged example materialization

The ordered JSON patches in `assets/examples/` are validator-test scenarios, not complete `submission.json` documents.
List them with `node scripts/materialize-example.mjs --list`, or materialize one deterministic submission with:

```bash
node scripts/materialize-example.mjs \
  --example transparent-pool-scoped-fee \
  --step fully-specified \
  --output submission.json
```

The materializer starts from the canonical template, applies every patch through the selected step, and validates the
result against `references/submission.schema.json`. It reads JSON only; it does not import, compile, or execute candidate
source. Run `node scripts/validate-submission.mjs submission.json` separately for the compatibility preflight.

Every `v0.5.1` scenario inherits the mandatory root `programmableFee` policy `1.1.0`. Examples may vary project economics,
but cannot replace the 10 bps canonical-pool platform allocation with an LP fee, transfer tax, router charge, app payment,
or alternative pool. A structurally ready example remains a proposal, not an audit, deployment, routing approval, live-fee
proof, or production release.

## Universal hard tests

Every prototype includes the baseline tests that match its real types and surfaces:

- zero, one, boundary, maximum and overflow-adjacent values for each bounded numeric type;
- unauthorized actors for protected actions and malformed forms of each accepted input/message;
- failure and recovery for every declared dependency;
- repeated calls, replay and duplicate initialization where stateful initialization exists;
- invariant call/revert counts where fuzzing is used, so reject-heavy fuzzing cannot masquerade as coverage; and
- event replay sufficient to reconstruct the public lifecycle where events are part of that lifecycle.

Add both token orderings only when supported; every exposed swap direction/exactness mode only for a swap surface;
malformed `hookData`, wrong PoolManager, cross-pool and callback tests only for a v4 hook; reverting/reentrant recipients
only where external value delivery exists; and runtime/initcode size only for deployable bytecode. A pure service or
indexer must instead prove its own authentication, data integrity, reorg/retry, dependency, failure and recovery paths.
